## **🚀 1. Phased Production Roadmap (The Order of Execution)**

To prevent architectural regression, production follows a strict bottom-up approach. Core domain layers and backing configurations must be locked and verified before delivery adapters and user interfaces are built.

### **Phase 1: Backing Infrastructure & Configuration Setup**

- **Core Focus:** Configuration file parsing (`config.ini`) and logger setup (`bibliomodel.log`).
- **Key Tasks:**
  - Implement configuration loading using the standard library `configparser` to parse borrowing limits (default: 3 books), default loan periods (default: 7 days), and daily fine rates (default: $2.00).
  - Initialize the logging configuration with standardized console and file output formatting.
- **Output Deliverable:** Functional bootstrapping layer capable of loading dynamic rules from `config.ini` and validating logging pipelines.

### **Phase 2: Bounded Domain Context & Core Models**

- **Core Focus:** Pure Object-Oriented domain entities (`BookEntity`, `ReaderEntity`, `LoanEntity`) protecting domain invariants.
- **Key Tasks:**
  - Implement status states (`Available`, `Loaned`, `Reserved` for Books; `Active`, `Suspended` for Readers).
  - Model the FIFO hold queue list inside `BookEntity` to manage reservations.
  - Build the pure `FineCalculator` domain service to compute late fees based on checkout/due/return timestamps.
  - Declare outbound repository interfaces (`ILibraryRepository`, `IConfigProvider`).
- **Output Deliverable:** Pure Python domain layer with 0 dependencies, encapsulating all core business objects and status transition validations.

### **Phase 3: Test-Driven Core Logic (Use Cases)**

- **Core Focus:** Application service use cases orchestrating user activities.
- **Key Tasks:**
  - Implement `CheckoutUseCase` checking reader status eligibility and book availability invariants.
  - Implement `ReturnUseCase` processing returns, calculating fees, and checking hold queues.
  - Implement `ReserveUseCase` queuing readers for occupied books.
  - Cover edge cases (such as backward dates, non-existent entity IDs) with strict pytest matrices.
- **Output Deliverable:** Complete business use-case engine with 100% logic coverage verified via failing specs before writing application logic.

### **Phase 4: Interface Adapters & Persistence Adapters**

- **Core Focus:** CLI interface parsing and atomic file persistence routines.
- **Key Tasks:**
  - Build the concrete `JSONPersistenceAdapter` implementing `ILibraryRepository` with atomic writing loops.
  - Implement the CLI controller parsing command lines (`loan`, `return`, `reserve`, `report`) using Python's `argparse`.
- **Output Deliverable:** Fully functional end-to-end local-first CLI tool serializing domain state changes into `db_backup.json` securely.

### **Phase 5: Diagnostics, Observability & Hardening**

- **Core Focus:** Performance telemetry and error-handling verification.
- **Key Tasks:**
  - Audit logs recording transactions with operator tags.
  - Validate database load recovery under simulated json corruption, checking the recovery rollover to `db_backup.json.bak`.
- **Output Deliverable:** Hardened production CLI executable ready for integration verification.

## **🧪 2. The Test-First (TDD) Lifecycle Gate**

Every code routine produced by developer resources or AI code generation assistants must comply with the strict Red-Green-Refactor sequence. The engineering loop explicitly forces test suite specifications to precede operational implementations.

### **2.1. The AI Prompt-to-Code Loop**

1. **The Specification Input:** The AI agent receives the exact module requirements, domain boundaries, and technical acceptance criteria.
2. **Step 1 (RED Phase):** The AI generates the test suite classes (Unit/Integration tests) mapping target interfaces and checking edge cases. _Code execution is blocked until this suite is run and fails._
3. **Step 2 (GREEN Phase):** The AI writes the _minimal required implementation code_ to satisfy the failing test conditions.
4. **Step 3 (REFACTOR Phase):** The AI optimizes the produced classes against architectural clean code guidelines (flake8/mypy typings, boundary constraints) while maintaining a green state across the test suite.

### **⚠️ Strict AI Implementation Constraint**

> [!WARNING]
> Under no circumstances shall the AI output production business logic before delivering its corresponding unit or integration test suite. Any code generated without preceding automated testing blocks will be flagged as an invalid build.

To maintain absolute architectural alignment and prevent model hallucination or context drift, copy the configuration schema below, populate its variables, and save it in your project workspace root directory as `claude.md` or `.cursorrules`.

```markdown
# BiblioModel — AI Engineering Context Rules

## 1. Role and Persona

You are a Staff Software Engineer and Expert Architect. You write clean, production-ready, highly performant code that strictly respects Object-Oriented Programming (OOP), SOLID principles, and Domain-Driven Design (DDD).

## 2. Core Constraints

- **Test-First Rule:** Always output the test file (using `pytest`) BEFORE writing the production implementation. If asked for a feature, provide the tests first, stop, wait for verification, then provide the business logic.
- **Architectural Isolation:** Hexagonal boundaries are absolute. Never import infrastructure components (e.g., CLI Controller, Persistence Adapters, ConfigParser Adapters) inside Domain Entities or Use Cases.
- **Data Durability:** Implement atomic write operations (serialize to `.tmp` first, then perform atomic operating-system replace to target `db_backup.json`) to prevent data corruption.
- **Zero Dependencies:** Use strictly standard Python library imports (`json`, `datetime`, `argparse`, `configparser`). No external packages except `pytest` for running tests.

## 3. Technology Stack Specifics

- Backend Framework: Python 3.10+ Standard Library (argparse CLI runner)
- Database Protocol: Local JSON serialization with atomic replace to db_backup.json
- Testing Strategy: pytest unit and integration files stored inside /tests/

## 4. Code Generation Quality Bar

- Every variable and class must follow the naming standards:
  - Domain Entity -> BookEntity, ReaderEntity, LoanEntity
  - Inbound Port -> ICheckoutUseCase, IReturnUseCase, IReserveUseCase
  - Outbound Port -> ILibraryRepository, IConfigProvider
  - Concrete Adapters -> JSONPersistenceAdapter, INIConfigAdapter
- Mask sensitive user parameters (PII) using standard formatting in logs. Do not leak plain-text names into logging outputs.
```
